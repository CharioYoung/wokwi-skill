# 09 · 真机外壳：把跑通的电路变成能拿在手里的东西

[English](09-enclosure.md) | **中文**

## 为什么要有这一节

仿真只能证明电路逻辑是对的。它不会告诉你板子该放在哪、盖上盖子之后 USB 线还能不能插进去、那个必须朝前看的超声波底下有没有东西托着。而这三件事决定了一个项目是留在浏览器标签页里，还是变成书架上的一个物件。

`diagram.json` 回答不了这些问题。它的坐标是**原理图空间里的布局提示**，不是毫米：在 Wokwi 里把器件挪 40 个单位，物理上什么都没动。所以外壳需要第二份带真实数字的文件。而这个模块的价值不在"能画个盒子"，在于**拿盒子去校验器件**：

| 校验 | 它拦下的失败 |
|---|---|
| `diagram.json` 里每个器件都有位置 | 打印出来发现板子放不进去 |
| 没有两个器件占同一块空间 | 装不起来 |
| 每个对外接口都能看见外面 | USB 线没处插，LED 只能照亮墙里侧 |
| 每个器件都有东西托着 | 盒子一翻过来它就掉 |
| 每个壳都是闭合的 | 切片器直接拒收，或打出来漏的 |
| 壁厚 ≥ 喷嘴 | 打出来是一层一碰就碎的壳 |

这些都由 `node scripts/check_enclosure.js` 报告，有问题退出码非零。图一张也报不出来。

## 1. `enclosure.json`

单位毫米，右手系：**x** 向右，**y** 向后，**z** 向上；原点是底壳的**外侧**前-左-下角。

```json
{
  "base":    { "w": 96, "d": 80, "h": 58, "wall": 2.4, "floor": 2.0, "fit": 0.4 },
  "lid":     { "on": true, "thick": 2.4, "lip": 3.0, "lipWall": 2.0 },
  "style":   { "color": "#f4c542", "accent": "#f59e0b" },
  "printer": { "bed": [220, 220], "layer": 0.2, "minWall": 0.8 },
  "margin": 0.4,
  "reach": 8,

  "parts":   [ { "id": "esp", "at": [20, 2.8, 2], "rot": 0 } ],
  "shelves": [ { "id": "beak", "at": [14, 2.4], "size": [56, 32], "z": 28, "thick": 2.4 } ],
  "bosses":  [ { "at": [6, 40], "d": 6.5, "hole": 3.2 } ],
  "cutouts": [ { "id": "vents", "face": "-y", "rect": [72, 40, 76, 52] } ]
}
```

### 1.1 `parts[]` —— 每颗器件实际坐在哪

| 字段 | 含义 |
|---|---|
| `id` | **必须**与 `diagram.json` 的 `parts[].id` 对上；两边任何一边多出来都是硬错误 |
| `at` | `[x, y, z]`，是器件的**最小角**，不是中心 |
| `rot` | `0`/`90`/`180`/`270`（绕 z）或 `"x90"`、`"y-90"`、`"x180"`…… 只允许 90 的整数倍：本文件所有装配检查都是轴对齐包围盒，斜一个角度，全部检查就都不准了 |

尺寸来自按 Wokwi 器件类型索引的表（`board-esp32-devkit-c-v4` 28×55×20、`wokwi-hc-sr04` 45×20×15、`wokwi-servo` 32.5×12.2×22.5、`wokwi-led` 5×5×8.6、`wokwi-buzzer` 12×12×9.5 ……）。表里没有的类型不会静悄悄给个 0×0：它会变成一个 12 mm 的立方体**外加一条警告**——错的盒子比一眼看得出的占位符更危险。

旋转先于摆放，转完的包围盒是精确的（`rotSize()` 把 cos/sin 取整，90° 不会留下 1e-16 的尾巴）。

### 1.2 `shelves[]` —— 必须朝外看的器件，靠什么托住

超声波得贴着前壁，又得躲开底板和板卡，于是它就悬在 28 mm 高处。没有层板，唯一的画法就是让它飘着——而飘着的器件是装不起来的器件。

```json
{ "id": "beak", "at": [14, 2.4], "size": [56, 32], "z": 28, "thick": 2.4 }
```

`at` 是平面上的最小角，`size` 是 `[宽, 深]`，`z` 是**上表面**高度，板子往下长 `thick`。层板会被自动"咬进"它贴着的墙 0.3 mm（沉进墙里比两个面共面好切片），并且**必须贴着至少一面墙**——悬在腔体正中的板子打出来需要支撑，那是另一个设计，所以是硬错误而不是警告。

### 1.3 `bosses[]` —— 螺柱，以及它隐含的盖子上的孔

```json
{ "at": [6, 40], "d": 6.5, "hole": 3.2, "h": 58 }
```

`h` 默认就是内腔高度，因为螺柱存在的意义就是够到盖子。盖子上那个过孔是**从同一个坐标推出来的**——不需要手写两份清单再去对齐。柱子往底板里沉 0.3 mm，而不是沉到底板**下面**：从 `z = -0.3` 起头的那一版，整机就靠四个小圆饼站着，真正的底板悬在空中。

### 1.4 `cutouts[]` —— 器件没要求的洞

散热槽、出线口、观察窗。`face` 取 `-y`/`+y`/`-x`/`+x`/`-z`，`rect` 是该面上的 `[u0, v0, u1, v1]`，`round: true` 变圆孔，`margin` 放大。

器件驱动的开口是自动的：尺寸表里每个 port 都声明了它朝哪一面、开口多大，够得着就开（`reach` 默认 8 mm）。埋在箱体里 20 mm 深处的接口会被报成 **blocked**，而不是悄悄开一个装饰性的洞。

## 2. 工作流

```bash
node -e "console.log(JSON.stringify(Enclosure.init(diagram),null,2))"   # 一份已经过检的草稿布局
node scripts/check_enclosure.js examples/duck-robot --parts              # 打印每颗器件的真实盒子
node scripts/check_enclosure.js                                          # 全部示例，有问题 exit 1
node scripts/sync_embed.js examples/duck-robot                           # enclosure.json → 页面数据块
node scripts/sync_enclosure.js                                           # enclosure.js → 所有页面
```

`check_enclosure.js --parts` 会把解析后的盒子逐条打出来——这是查"屏幕上看着挺对"其实差 6 mm 最快的方式：

```
esp      board-esp32-devkit-c-v4   28.0×55.0×20.0  at [20.0, 2.8, 2.0]  box [20.0,2.8,2.0]..[48.0,57.8,22.0]
hc       wokwi-hc-sr04             45.0×20.0×15.0  at [20.0, 2.8, 28.0] box [20.0,2.8,28.0]..[65.0,22.8,43.0]
```

### 2.1 怎么读报告

| `k` | 含义 | 怎么改 |
|---|---|---|
| `missing-part` | 在 `diagram.json` 里，`enclosure.json` 没给它位置 | 给它一个位置 |
| `stray-part` | 在 `enclosure.json` 里，`diagram.json` 里没有 | 改名只改了一边 |
| `outside` | 盒子越过了腔壁、底板或盖子 | 往里挪 |
| `interfere` | 两个盒子占同一块空间 | 挪开一个，报告里有重叠尺寸 |
| `floating` | 底下什么都没有 | 放到底板、层板、另一个器件上，或压进墙上的孔 |
| `blocked` | 某个接口够不到墙 | 转个方向，或挪到那面墙边 |
| `cutout-edge` | 开口离墙边不足 1.2 mm | 会破边 |
| `cutout-clash` | 两个开口重叠 | 合并成一条长槽 |
| `shelf` | 层板没贴墙 / 出了腔体 / 穿过器件 | 改数字 |
| `mesh` | 壳没闭合，或某个面三角化后面积不对 | 通常是一面开孔太多，合并它们 |
| `thin` / `bed` | 壁厚小于 `minWall`，或超出热床 | 加厚，或缩放 |

`floating` 是最容易让人意外的，也是最值得存在的：一颗悬在底板上方 3 mm 的器件，能通过所有"放不放得下"的检查，然后照样掉出来。

### 2.2 在查看器里长什么样

页面会多出一张卡片，数据源就是同一份 `enclosure.json`：

- **外观** —— 外部视图。层板在这个视图里不画：内部板子只能透过去看到一个洞，而画家算法会把那块小板画成横在开口上的一道杠。
- **剖视 · 器件怎么放** —— 去掉前壁和盖子，画出器件并标注 id。
- **爆炸** —— 盖子抬起。
- **↓ 下载 .stl** —— 二进制 STL，底壳与盖子**并排摆好**，盖子翻面（绕 x 转 180°），让平的顶面朝下贴床、口沿朝上。反着打就是 96×80 悬空桥。

problems / warns 会以红/黄条出现在卡片上，措辞与命令行一致。如果元数据写着"全部落位、互不干涉"，下面却是一条红色错误，那页面就是在骗自己——所以只要 `problems` 非空，那一行就变成"有待修的问题"。

## 3. 几何是怎么造出来的（只有要改它时才需要看）

- **两个闭合壳 + 若干小件。** `base`、`lid`、`boss`、`shelf` 各自是闭合流形。它们从不做 CSG 合并——那需要几何内核——而是在搭接处故意重叠 0.3 mm，切片器会并集。
- **面 = 轴对齐矩形减凸孔。** 这种形状有精确分解：按每个孔顶点的 `y` 把矩形切成水平条带；一条带内，凸孔就是一条直线段，剩下的材料是梯形。没有桥接、没有零宽缝、没有可能漏掉的耳朵。桥接 + 耳切那条路仍然保留，作为"轮廓不是矩形"的面（螺柱顶上的圆环）的兜底。
- **每个面两道审计。** 面积（三角之和必须等于矩形减孔，误差 0.2% 内）与闭合（每条有向边恰有一个反向孪生）。曾经四个圆孔用桥接缝织在一起，得到的面边边相连完全闭合，却把 7680 mm² 里的 1192 mm² 盖了两遍——闭合检查看不见这种事，面积审计能。
- **T 型顶点会被焊掉。** 条带三角化会在每个孔高度上切分面的边界，旁边的墙于是有一个顶点落在边的中间；切片器会把这读成非流形接缝。`weldTJunctions()` 负责把长边拆开，并迭代到不动点。
- **有符号体积**决定绕向。内翻的壳形状正确、法线全黑。

## 4. 渲染器自己的规矩

- 正交轨道相机 + 画家算法 + 一个三角形一个 `<polygon>`——所以输出能在假 DOM 里测，也能在 git 里 diff。
- **开背面剔除。** 不开的话，每个孔都会露出自己孔壁的近侧，像一弯墙色的月牙；墙后面的螺柱也会透出来。
- **朝内腔的面压暗**（0.72）。远侧墙是同样的塑料、同样的灯，不压暗的话"孔里看得见内部"和"孔被填死了"是同一片像素。
- 深度是 `Y·cos(pitch) − Z·sin(pitch)`，越大越远。z 项符号写反会把 z=58 的螺柱画在 z=66 的盖子上面——一根浮在闭合盒子上的柱子，而画面看上去几乎是对的。

## 5. 说清楚边界

- **只管盒子。** 器件是轴对齐盒子，壳体是矩形杯。圆形机身、卡扣、铰链、鸭子那种曲面脑袋：这里没有。你得到的是一个**能证明装得下**的机身。
- **没有 CSG。** 壳之间是重叠而不是合并；STL 是一组闭合体，由切片器并集。它不是单一流形，`checkMesh` 也是逐壳判定。
- **一个面上开不了太多孔。** 超过大约 10–12 个，条带分解本身还行，但兜底路径可能失败；报告会说出来，而不是交给你一个破面。
- **`enclosure.json` 是可选的。** 面包板项目、32 个舵机挂在裸架上的环形装置，本来就没有机身；数据块留空，卡片自动隐藏。绝不要把别的项目的盒子留在页面上——没有文件时 `sync_embed.js` 会把数据块清空。
